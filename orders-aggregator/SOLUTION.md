# Решение

## Что сделано

`GET /customers/:id/daily-totals` по каждому дню отдаёт суммы оплаченных (`paid`) заказов:

- `gross` — сумма `amount` до скидки;
- `net` — сколько клиент фактически заплатил (`amountPaid`);
- `discount` — `gross - net`;
- `total` оставлен для совместимости и равен `gross`.

Суммы в рублях с точностью до копейки. Внутри сервиса по-прежнему целые копейки. Новая колонка `orders.amount_paid_kop` (миграция `002_discounts.sql`).

Откуда берётся оплата:

- есть `amountPaid` — это источник истины, даже если рядом лежит `discountPercent`;
- есть только `discountPercent` — `amount * (1 - percent / 100)`, доля копейки отбрасывается;
- нет обоих полей (старые заказы) — скидки не было, `net = gross`.

`amount` и `discountPercent` принимаются и числом, и строкой, как уже умеет `amount`.

День заказа — календарная дата `createdAt` в таймзоне клиента **на этот момент**, через `Intl`. Одно смещение на весь диапазон больше не используется: у зоны со сменой летнего времени оно разное в разные дни и ещё зависит от того, когда пришёл запрос.

Запись версии заказа — один `INSERT ... ON CONFLICT DO UPDATE ... WHERE orders.updated_at < excluded.updated_at`. Равная или более старая версия не перезаписывает сохранённую. Условие стоит в SQL, потому что вебхуки приходят параллельно: проверка «прочитал — потом записал» в коде проигрывает гонку.

`createContainer(db, api)` и интерфейс `OrdersApi` не менялись.

## Причина расхождения по клиенту c_7

`GET /customers/c_7` возвращает `Europe/Berlin`.

29 марта 2026 — последнее воскресенье марта, в этот день в 01:00 UTC Берлин переходит с CET (UTC+1) на CEST (UTC+2). Старый код брал смещение один раз:

```ts
const offset = tzOffsetMinutes(timezone, new Date());
```

`new Date()` — момент запроса. В ноябре Берлин снова на UTC+1, и это зимнее смещение применялось ко всем заказам конца марта.

- 27 и 28 марта ещё действительно UTC+1, поэтому суммы сходились с платёжной системой до копейки.
- С 29 марта 01:00 UTC заказы между 22:00 и 23:00 UTC — это уже следующие локальные сутки (00:00–01:00 CEST), а при UTC+1 они оставались на предыдущем дне. Из-за этого 29, 30 и 31 марта не сходились.

Платёжная система режет сутки по местному времени каждого платежа, то есть по смещению в момент `createdAt`, а не по смещению «сейчас».

Как нашёл: таймзона клиента из внешнего API, дата перевода часов в ЕС, заказы `c_7` около 22:40 UTC 29–31 марта. Для этих заказов дата в `Europe/Berlin` и дата по фиксированным +60 минутам расходятся ровно на сутки. Дни без таких заказов совпадают до копейки — это как раз формулировка жалобы.

## Что ещё заметил

- В списке 5030 заказов, 52 страницы. В конце API отдаёт не `nextCursor: null`, а пустую страницу с тем же курсором. Клиент это уже учитывает. Синк забрал всё: `received: 5030`, `applied: 5030`, `invalid: 0`.
- Часть `amount` и `discountPercent` приходит строками (`"3100.00"`, `"33"`), часть `createdAt` — без зоны. По контракту сервиса такая дата — UTC.
- У 1177 заказов полей скидки нет. На снимке, где поля есть, `amountPaid` совпадает с `amount * (1 - discountPercent / 100)`.
- `Math.floor(rub * 100)` теряет копейку на значениях вроде `19.99` и `4723.9`: в IEEE `4723.9 * 100` равно `472389.99999999994`. Это не «доля копейки», а погрешность двоичной дроби. `toKop` по-прежнему отбрасывает настоящую долю (`10.999` → 1099) и не срезает целую копейку.
- Вебхуков 92, все по `c_7`. Они повторяются, идут не по порядку и сразу в несколько соединений. У одного заказа несколько версий: статус (`pending` → `paid` → `refunded`) и скидка меняются при том же `createdAt`. Побеждает больший `updatedAt`.
- Из-за гонки в старой проверке версии в базу попала промежуточная скидка. `gross` при этом был верным, а `net` на 27 и 31 марта — нет. Повторная отправка тех же вебхуков после исправления итог не меняет.
- Лимит внешнего API — 5 rps: и HTTP 429, и 200 с телом `{ "error": "rate_limited" }`. Клиент это уже обрабатывает.

## Допущения

- Сутки считаются по `createdAt`, не по времени оплаты. Так уже устроены тесты. Жалоба это подтверждает: расходились только дни на границе перевода часов, остальные совпадали до копейки, значит набор заказов был верный и сдвигалась граница суток.
- Если пришли и `amountPaid`, и `discountPercent`, в статистику идёт `amountPaid`.
- Заказ без обоих полей считается без скидки.
- `discount` дня — разница дневных сумм. В целых копейках это то же самое, что сумма скидок заказов.
- Событие с тем же `updatedAt`, что уже сохранено, не заменяет запись.

## Что бы доделал при наличии времени

- Не хранить таймзону клиента вечно: смена зоны во внешнем API сейчас не подхватывается.
- Отдельное поле версии, если у двух разных событий совпадёт `updatedAt`.
- В ответ синка или в лог — не только счётчик `invalid`, но и идентификаторы отброшенных заказов.
- Прогон против внешнего API в CI. Сейчас интеграционные тесты ходят в фейк, живой прогон описан ниже.

## Как проверял

- `npm test` — 35 тестов, все зелёные. Новые покрывают скидку (в том числе пример `2500 / 412.5 / 2087.5`), строковый процент без `amountPaid`, последнюю версию оплаты, копейку на `4723.9`, перевод часов в `Europe/Berlin` (22:40 UTC 28 марта остаётся 28-м, 22:40 UTC 29 марта попадает на 30-е, 22:40 UTC 31 марта — уже 1 апреля) и параллельные вебхуки.
- `npm run typecheck` — без ошибок.
- Чистая база, сервис, `POST /sync` до ответа `{ "pages": 52, "received": 5030, "applied": 5030, "stale": 0, "invalid": 0 }`.
- `docker compose run --rm orders-api webhooks --target http://host.docker.internal:3000/webhooks/order` — `webhooks sent: 92, responses: {"200":92}`.
- `GET /customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31` совпал с отдельным пересчётом: страницы `GET /orders` плюс тела вебхуков, копейки и календарная дата в `Europe/Berlin`. Ответ лежит в `result.json`. Повторная отправка тех же вебхуков этот ответ не изменила.
